웹사이트를 독립적인 UI 단위로 나누고 데이터를 전달하기

공개

2026년 9월 14일

6 컴포넌트 개요

React 애플리케이션은 컴포넌트(component)라는 독립적인 UI 단위로 구성됩니다. 컴포넌트는 화면의 일부를 설명하는 JavaScript 함수이며 JSX를 반환합니다. 작은 아이콘과 버튼부터 내비게이션, 프로젝트 카드, 사이드바, 페이지 전체까지 컴포넌트가 될 수 있습니다.

function Welcome() {
  return <h1>React 프로젝트에 오신 것을 환영합니다.</h1>;
}

일반 JavaScript 함수와 비교하면 React 함수 컴포넌트에는 두 가지 중요한 관례가 있습니다.

  1. 컴포넌트 이름은 대문자로 시작합니다.
  2. 화면 구조를 표현하는 JSX를 반환합니다.

React 공식 문서는 React 애플리케이션의 모든 UI 조각을 컴포넌트로 구성할 수 있다고 설명합니다. 컴포넌트는 재사용 목적뿐 아니라 코드를 역할별로 조직하고 유지보수하기 위해서도 사용합니다. 한 번만 등장하는 큰 화면 영역도 독립적인 책임이 있다면 컴포넌트로 분리할 수 있습니다. React 공식 문서: Your First Component

노트컴포넌트의 핵심

컴포넌트는 JSX를 짧게 자르는 기술이 아닙니다. 하나의 명확한 역할을 가진 UI 단위에 이름을 붙이고, 입력 데이터에 따라 화면을 계산하도록 만드는 설계 단위입니다.

7 컴포넌트로 만들 수 있는 웹사이트 영역

웹사이트 종류 컴포넌트로 분리할 수 있는 영역
개인 포트폴리오 SiteHeader, Hero, SkillBadge, ProjectCard, Contact, SiteFooter
쇼핑몰 ProductCard, Price, CartItem, CategoryMenu, OrderSummary
블로그 PostCard, AuthorProfile, Tag, Comment, Pagination
대시보드 Sidebar, MetricCard, ChartPanel, FilterBar, UserMenu
학교 사이트 CourseCard, ProfessorProfile, ScheduleTable, NoticeCard
예약 서비스 PlaceCard, DateSelector, GuestCounter, BookingSummary

컴포넌트 분리는 화면에서 반복되는 모양만 찾는 작업이 아닙니다. 다음 질문으로 경계를 판단합니다.

  • 이 영역을 한 문장으로 설명할 수 있는가?
  • 독립적인 데이터를 입력받는가?
  • 다른 페이지에서도 사용할 가능성이 있는가?
  • 수정 이유가 다른 영역과 구별되는가?
  • 부모 화면이 세부 마크업 때문에 읽기 어려워졌는가?
  • 별도의 접근성 역할이나 스타일 책임이 있는가?

너무 큰 컴포넌트는 여러 책임이 섞이고, 지나치게 작은 컴포넌트는 파일과 이름만 늘려 흐름을 찾기 어렵게 합니다. 처음에는 Header, Hero, 프로젝트 영역, Contact, Footer처럼 시각적·의미적으로 분명한 영역부터 나눕니다.

8 컴포넌트 선언과 사용

8.1 함수 컴포넌트 선언

function Profile() {
  return (
    <article className="profile">
      <img
        className="profile__image"
        src="/images/profile.jpg"
        alt="홍길동 프로필"
      />
      <h2>홍길동</h2>
      <p>프론트엔드 개발을 공부합니다.</p>
    </article>
  );
}

함수 이름 Profile이 컴포넌트 이름이 됩니다. 컴포넌트는 JSX에서 사용자 정의 태그처럼 사용합니다.

function App() {
  return (
    <main>
      <h1>개발자 소개</h1>
      <Profile />
    </main>
  );
}

소문자로 시작하는 <profile />은 사용자 컴포넌트로 인식되지 않습니다. React는 소문자 태그를 div, section, button 같은 브라우저 내장 요소로 처리하고 대문자로 시작하는 태그를 JavaScript 컴포넌트로 처리합니다.

8.2 컴포넌트 중첩

컴포넌트는 다른 컴포넌트를 렌더링할 수 있습니다.

function SiteHeader() {
  return (
    <header className="site-header">
      <a href="#top">홍길동.dev</a>
      <Navigation />
    </header>
  );
}

function Navigation() {
  return (
    <nav aria-label="주요 메뉴">
      <a href="#about">소개</a>
      <a href="#projects">프로젝트</a>
      <a href="#contact">연락처</a>
    </nav>
  );
}

SiteHeader는 사이트 머리말이라는 큰 책임을 담당하고 Navigation은 페이지 이동 링크라는 더 구체적인 책임을 담당합니다.

8.3 컴포넌트 안에서 컴포넌트를 선언하지 않기

다음처럼 렌더링되는 함수 안에 다른 컴포넌트를 선언하지 않습니다.

function App() {
  // 잘못된 구조: App이 렌더링될 때마다 새로운 Profile 함수가 만들어짐
  function Profile() {
    return <p>홍길동</p>;
  }

  return <Profile />;
}

컴포넌트는 모듈의 최상위 수준에 선언합니다.

function Profile() {
  return <p>홍길동</p>;
}

function App() {
  return <Profile />;
}

컴포넌트를 내부에 선언하면 부모가 렌더링될 때마다 다른 컴포넌트 타입으로 취급될 수 있어 상태 초기화와 성능 문제를 만들 수 있습니다. 부모 데이터가 필요하면 컴포넌트 정의를 중첩하지 말고 Props로 전달합니다.

9 컴포넌트 파일 분리

모든 컴포넌트를 App.jsx에 작성하면 프로젝트가 커질수록 찾고 수정하기 어려워집니다. 의미 있는 단위로 파일을 분리합니다.

src/
├─ components/
│  ├─ SiteHeader.jsx
│  ├─ Navigation.jsx
│  ├─ Hero.jsx
│  ├─ SkillBadge.jsx
│  ├─ ProjectCard.jsx
│  ├─ Contact.jsx
│  └─ SiteFooter.jsx
├─ App.jsx
├─ main.jsx
└─ index.css

파일 이름은 컴포넌트 이름과 같게 작성하면 검색하기 쉽습니다. ProjectCard.jsx에는 ProjectCard 컴포넌트의 책임과 관련된 코드만 둡니다.

9.1 default export와 import

한 파일의 대표 컴포넌트를 default export할 수 있습니다.

// components/SiteHeader.jsx
export default function SiteHeader() {
  return (
    <header>
      <a href="#top">홍길동.dev</a>
    </header>
  );
}

가져올 때 중괄호를 사용하지 않으며 가져오는 쪽에서 이름을 정할 수 있습니다.

// App.jsx
import SiteHeader from "./components/SiteHeader.jsx";

9.2 named export와 import

한 파일에서 여러 값을 이름과 함께 export할 수 있습니다.

// components/Icons.jsx
export function GitHubIcon() {
  return <span aria-hidden="true">GH</span>;
}

export function ExternalLinkIcon() {
  return <span aria-hidden="true">↗</span>;
}

named import에는 정확한 이름과 중괄호를 사용합니다.

import { GitHubIcon, ExternalLinkIcon } from "./components/Icons.jsx";

default와 named 방식 중 하나만 정답은 아닙니다. 한 파일에 대표 컴포넌트 하나를 두는 수업 프로젝트에서는 default export가 단순합니다. 유틸리티나 관련된 작은 아이콘처럼 여러 값을 한 모듈에서 제공할 때는 named export가 명시적입니다. export 방식과 import 문법이 일치해야 합니다. React 공식 문서: Importing and Exporting Components

10 Props 개요

Props는 부모 컴포넌트가 자식 컴포넌트에 전달하는 입력 데이터입니다. HTML 요소에 src, alt, className 같은 속성을 전달하는 것처럼 사용자 컴포넌트에도 원하는 이름의 Props를 전달할 수 있습니다.

function App() {
  return (
    <Profile
      name="홍길동"
      role="프론트엔드 개발자"
      imageUrl="/images/profile.jpg"
    />
  );
}

부모인 App이 자식인 Profile에 name, role, imageUrl을 전달합니다. Profile 함수는 하나의 props 객체를 매개변수로 받습니다.

function Profile(props) {
  return (
    <article>
      <img src={props.imageUrl} alt={`${props.name} 프로필`} />
      <h2>{props.name}</h2>
      <p>{props.role}</p>
    </article>
  );
}

Props는 일반 함수의 인자와 비슷합니다. 컴포넌트라는 UI 공식을 만들고 Props로 입력값을 바꾸면 같은 구조에서 다른 결과를 얻습니다. React 공식 문서: Passing Props to a Component

11 Props 구조 분해 할당

대부분의 컴포넌트는 props 객체에서 필요한 값을 구조 분해합니다.

function Profile({ name, role, imageUrl }) {
  return (
    <article>
      <img src={imageUrl} alt={`${name} 프로필`} />
      <h2>{name}</h2>
      <p>{role}</p>
    </article>
  );
}

다음 두 코드는 같은 의미입니다.

function Profile(props) {
  const name = props.name;
  const role = props.role;
}
function Profile({ name, role }) {
}

구조 분해 괄호를 빠뜨리면 의미가 달라집니다.

// name prop만 받는 것이 아니라 props 객체 전체를 name이라는 변수로 받음
function Profile(name) {
  return <h2>{name}</h2>; // 객체 렌더링 오류
}

올바른 코드는 다음과 같습니다.

function Profile({ name }) {
  return <h2>{name}</h2>;
}

12 다양한 Props 값 전달

사용자 컴포넌트에는 문자열뿐 아니라 숫자, 불리언, 객체, 배열, 함수와 JSX를 전달할 수 있습니다.

12.1 문자열

<ProjectCard title="학습 기록 서비스" status="개발 중" />

고정 문자열은 따옴표로 전달합니다.

12.2 숫자와 표현식

<Avatar name="홍길동" size={120} />
<Progress completed={3} total={15} />

숫자와 JavaScript 표현식은 중괄호를 사용합니다. size="120"은 문자열이고 size={120}은 숫자입니다.

12.3 불리언

<ProjectCard featured={true} />
<ProjectCard featured />

값 없이 prop 이름만 작성하면 true다. false는 명시적으로 전달합니다.

<ProjectCard featured={false} />

12.4 객체

const project = {
  title: "학습 기록 서비스",
  status: "개발 중",
  description: "날짜별 학습 기록을 관리합니다.",
};

<ProjectCard project={project} />

객체 리터럴을 바로 전달할 때 겹친 중괄호처럼 보일 수 있습니다.

<ProjectCard
  project={{
    title: "일정 관리 서비스",
    status: "기획 중",
  }}
/>

바깥 중괄호는 JSX 표현식, 안쪽 중괄호는 JavaScript 객체입니다.

12.5 배열

<ProjectCard technologies={["HTML", "CSS", "React"]} />

배열을 전달할 수 있습니다. 배열을 화면 목록으로 변환하는 map()과 key는 7주차에서 자세히 다룹니다.

12.6 함수

<button onClick={handleClick}>저장</button>

함수도 prop으로 전달할 수 있습니다. 자식에서 발생한 사용자 행동을 부모가 처리하도록 연결할 때 사용합니다. 이벤트 처리와 State는 5주차에서 구체적으로 다룹니다.

13 기본값을 가진 Props

구조 분해 할당에서 기본값을 지정할 수 있습니다.

function Avatar({ name, imageUrl, size = 120 }) {
  return (
    <img
      src={imageUrl}
      alt={`${name} 프로필`}
      width={size}
      height={size}
    />
  );
}

size를 생략하면 120을 사용합니다.

<Avatar name="홍길동" imageUrl="/images/profile.jpg" />

기본값은 prop이 생략되거나 undefined일 때 사용됩니다. null이나 0을 명시적으로 전달하면 기본값으로 바뀌지 않습니다.

<Avatar name="홍길동" imageUrl="/images/profile.jpg" size={0} />

0은 유효한 입력값으로 그대로 전달됩니다.

14 Props는 읽기 전용이다

컴포넌트는 받은 Props를 직접 변경하면 안 됩니다.

function ProjectCard({ project }) {
  // 잘못된 예: 부모가 전달한 객체 변경
  project.status = "완료";

  return <p>{project.status}</p>;
}

Props는 해당 렌더링의 읽기 전용 스냅샷으로 취급합니다. 화면을 바꾸려면 부모가 새로운 값을 전달하거나 이후에 배울 State 업데이트를 사용합니다.

function ProjectCard({ project }) {
  const statusLabel = `현재 상태: ${project.status}`;
  return <p>{statusLabel}</p>;
}

입력값을 이용해 새로운 지역 값을 계산하는 것은 안전합니다. React 공식 규칙은 Props와 State를 직접 변경하지 않는 불변값으로 다룰 것을 요구합니다. React 공식 규칙: Components and Hooks must be pure

15 부모에서 자식으로 흐르는 데이터

Props는 기본적으로 부모에서 자식 방향으로 흐릅니다.

App
 ├─ SiteHeader

 ├─ Projects

const developer = {
  name: "홍길동",
  role: "프론트엔드 개발자",

Hero는 developer 데이터가 어디서 왔는지, 나중에 어떻게 바뀌는지 알 필요가 없습니다. 전달된 값을 기준으로 UI를 계산합니다. 부모는 어떤 데이터를 줄지 결정하고 자식은 어떻게 표시할지 결정합니다. 이 분리는 컴포넌트를 독립적으로 이해하고 재사용하기 쉽게 합니다.

16 children으로 JSX 전달

컴포넌트 태그 사이에 작성한 내용은 특별한 children prop으로 전달됩니다.

function Card({ children }) {
  return <div className="card">{children}</div>;
}

function App() {
  return (
    <Card>
      <h2>학습 기록 서비스</h2>
      <p>날짜별 학습 내용을 기록합니다.</p>
    </Card>
  );
}

Card는 내부에 어떤 콘텐츠가 들어오는지 구체적으로 알지 않아도 됩니다. 부모가 전달한 children을 지정된 위치에 표시합니다. 공식 문서는 children을 부모가 JSX로 채울 수 있는 “구멍”에 비유합니다.

children은 다음과 같은 웹사이트 영역을 만들 때 유용합니다.

  • 공통 카드 외곽선
  • Modal의 본문
  • Panel이나 Section의 내부 콘텐츠
  • 페이지의 공통 Container
  • 알림 상자
  • 레이아웃 wrapper

16.1 재사용 가능한 Section 컴포넌트

function Section({ id, title, children }) {
  const titleId = `${id}-title`;

  return (
    <section id={id} aria-labelledby={titleId} className="section">
      <h2 id={titleId}>{title}</h2>
      <div className="section__content">{children}</div>
    </section>
  );
}
function App() {
  return (
    <main>
      <Section id="about" title="소개">
        <p>웹 표준과 React를 공부하고 있습니다.</p>
      </Section>

      <Section id="projects" title="프로젝트">
        <ProjectCard
          title="학습 기록 서비스"
          description="날짜별 학습 내용을 기록합니다."
        />
      </Section>
    </main>
  );
}

Section은 id와 제목이라는 정형 데이터는 Props로 받고, 자유롭게 바뀌는 본문은 children으로 받습니다.

17 Props 펼치기

JSX spread 문법으로 객체의 여러 속성을 한 번에 전달할 수 있습니다.

const project = {
  title: "학습 기록 서비스",
  status: "개발 중",
  description: "날짜별 학습 내용을 기록합니다.",
};

<ProjectCard {...project} />

이는 다음과 같습니다.

<ProjectCard
  title={project.title}
  status={project.status}
  description={project.description}
/>

Wrapper 컴포넌트가 받은 Props를 그대로 전달할 수도 있습니다.

function FeaturedProject(props) {
  return (
    <div className="featured-project">
      <ProjectCard {...props} />
    </div>
  );
}

spread는 간결하지만 어떤 값이 전달되는지 숨길 수 있습니다. 모든 컴포넌트에서 습관적으로 사용하지 않습니다. 컴포넌트의 공개 입력을 명확히 보여주는 것이 중요한 경우에는 Props를 직접 작성합니다.

18 웹사이트 영역별 컴포넌트 설계

18.1 Header: 사이트 이름과 내비게이션 데이터

function SiteHeader({ siteName }) {
  return (
    <header className="site-header">
      <a className="site-logo" href="#top">{siteName}</a>
      <Navigation />
    </header>
  );
}

function Navigation() {
  return (
    <nav aria-label="주요 메뉴">
      <ul className="navigation-list">
        <li><a href="#about">소개</a></li>
        <li><a href="#projects">프로젝트</a></li>
        <li><a href="#contact">연락처</a></li>
      </ul>
    </nav>
  );
}

사이트마다 달라지는 이름은 prop으로 받고 메뉴 구조는 현재 컴포넌트가 직접 렌더링합니다. 메뉴도 데이터에 따라 달라져야 한다면 이후 배열 prop으로 확장할 수 있습니다.

18.2 Hero: 개발자 객체 전달

function Hero({ developer }) {
  return (
    <section className="hero" id="about" aria-labelledby="hero-title">
      <div>
        <p>{developer.role}</p>
        <h1 id="hero-title">안녕하세요, {developer.name}입니다.</h1>
        <p>{developer.message}</p>
      </div>

      <Avatar
        name={developer.name}
        imageUrl={developer.imageUrl}
        size={320}
      />
    </section>
  );
}

function Avatar({ name, imageUrl, size = 160 }) {
  return (
    <img
      className="avatar"
      src={imageUrl}
      alt={`${name}의 프로필`}
      width={size}
      height={size}
    />
  );
}

Hero는 개발자 전체 데이터를 받고 그중 이미지 표현은 Avatar에 다시 필요한 값만 전달합니다. 하나의 거대한 컴포넌트보다 역할을 나누되 데이터 흐름은 위에서 아래로 유지합니다.

18.3 상태 배지: 작은 재사용 컴포넌트

function StatusBadge({ status = "기획 중" }) {
  const statusClassName = `status-badge status-badge--${status}`;

  return <span className={statusClassName}>{status}</span>;
}

한글 상태값을 class에 직접 쓰면 CSS 선택과 유지보수가 불편할 수 있습니다. 화면 문구와 스타일용 값을 분리하면 더 안정적입니다.

function StatusBadge({ label, tone = "neutral" }) {
  return (
    <span className={`status-badge status-badge--${tone}`}>
      {label}
    </span>
  );
}
<StatusBadge label="기획 중" tone="neutral" />
<StatusBadge label="개발 중" tone="progress" />
<StatusBadge label="완료" tone="success" />

이 패턴은 쇼핑몰의 “품절”, 게시판의 “공지”, 대시보드의 “정상”과 같은 상태 표시에 재사용할 수 있습니다.

18.4 ProjectCard: 같은 구조로 다른 데이터 표현

function ProjectCard({
  title,
  status,
  description,
  imageUrl,
  demoUrl,
  repositoryUrl,
}) {
  return (
    <article className="project-card">
      <img
        className="project-card__image"
        src={imageUrl}
        alt={`${title} 실행 화면`}
      />

      <div className="project-card__content">
        <StatusBadge label={status} tone="progress" />
        <h3>{title}</h3>
        <p>{description}</p>

        <div className="project-card__links">
          <a href={demoUrl}>실행 화면</a>
          <a href={repositoryUrl}>소스 코드</a>
        </div>
      </div>
    </article>
  );
}

같은 컴포넌트를 서로 다른 Props로 사용할 수 있습니다.

function Projects() {
  return (
    <section id="projects" aria-labelledby="projects-title">
      <h2 id="projects-title">프로젝트</h2>

      <div className="project-grid">

          repositoryUrl="https://github.com/example/portfolio"

마크업을 두 번 복사하지 않았기 때문에 카드 구조나 접근성 설명을 ProjectCard 한곳에서 수정할 수 있습니다. 7주차에는 프로젝트 배열을 map()으로 변환하여 반복 코드를 제거합니다.

18.5 Contact와 Footer

function Contact({ email, githubUrl }) {
  return (
    <section id="contact" aria-labelledby="contact-title">
      <h2 id="contact-title">연락처</h2>
      <address>
        <a href={`mailto:${email}`}>{email}</a>
        <a href={githubUrl}>GitHub</a>
      </address>
    </section>
  );
}

function SiteFooter({ owner, year = 2026 }) {
  return (
    <footer className="site-footer">
      <small>&copy; {year} {owner}</small>
    </footer>
  );
}

year = 2026은 prop이 생략됐을 때 사용하는 예측 가능한 기본값입니다. 실제 서비스에서 현재 연도를 사용하려면 애플리케이션의 시작 지점이나 부모에서 값을 결정해 prop으로 전달할 수 있습니다.

<SiteFooter owner="홍길동" year={2026} />

19 포트폴리오 전체 조립

App은 페이지 전체 데이터와 큰 구조를 관리합니다. 세부 마크업은 각 컴포넌트에 위임합니다.

import SiteHeader from "./components/SiteHeader.jsx";
import Hero from "./components/Hero.jsx";
import Projects from "./components/Projects.jsx";
import Contact from "./components/Contact.jsx";

20 실행 결과: 컴포넌트와 Props로 만든 프로젝트 카드

다음 화면의 세 카드는 하나의 ProjectCard 컴포넌트를 반복 사용한 결과입니다. 컴포넌트 구조는 같지만 부모가 전달하는 title, description, status, tags Props가 달라 서로 다른 프로젝트로 렌더링됩니다.

실행 결과를 새 창에서 보기

이 방식은 포트폴리오의 프로젝트 카드뿐 아니라 기술 배지, 경력 항목, 후기, 상품 카드처럼 모양은 같고 데이터만 달라지는 영역에 적용할 수 있습니다. 부모 컴포넌트는 페이지의 데이터와 배열을 관리하고, 자식 컴포넌트는 전달받은 Props를 일관된 UI로 표현합니다.

21 컴포넌트 API 설계

Props는 컴포넌트의 공개 API다. 이름과 구조를 신중하게 설계합니다.

21.1 역할이 드러나는 이름

// 의미가 불분명함
<ProjectCard text="학습 기록" value="개발 중" data="..." />
// 역할이 명확함
<ProjectCard
  title="학습 기록"
  status="개발 중"
  description="날짜별 학습 내용을 기록합니다."
/>

21.2 너무 많은 불리언 Props 피하기

<Button primary large rounded fullWidth danger />

서로 충돌하는 조합을 만들 수 있습니다. 의미 있는 variant와 size로 표현하는 편이 명확합니다.

<Button variant="danger" size="large" fullWidth>
  삭제
</Button>

21.3 표시 데이터와 스타일 설정 구분

status="완료"는 사용자에게 보여줄 데이터이고 tone="success"는 시각적 역할입니다. 하나의 문자열에 두 책임을 섞지 않으면 다국어와 디자인 변경에 대응하기 쉽습니다.

22 컴포넌트 합성과 재사용의 균형

재사용 가능성을 높이겠다고 모든 요소를 범용 컴포넌트로 만들 필요는 없습니다.

// 지나치게 추상적인 예
<Box display="flex" gap="medium" color="surface">
  <Text as="h2" size="large">프로젝트</Text>
</Box>

수업 초기에는 의미가 분명한 HTML과 도메인 컴포넌트를 우선합니다.

<section className="projects">
  <h2>프로젝트</h2>
  <ProjectCard ... />
</section>

여러 화면에서 같은 패턴이 실제로 반복되고 변경 이유가 같을 때 공통 컴포넌트로 추출합니다. “언젠가 재사용할 것 같다”는 이유만으로 너무 일찍 추상화하지 않습니다.

23 자주 발생하는 오류

23.1 컴포넌트 이름을 소문자로 작성

function projectCard() {
  return <article>프로젝트</article>;
}

<projectCard />

대문자로 시작하도록 고칩니다.

function ProjectCard() {
  return <article>프로젝트</article>;
}

<ProjectCard />

23.2 컴포넌트 정의를 부모 안에 중첩

컴포넌트는 모듈 최상위에 선언하고 데이터는 Props로 전달합니다.

23.3 default와 named import 혼동

// default export
export default function Hero() {}

// 올바른 import
import Hero from "./Hero.jsx";
// named export
export function Hero() {}

// 올바른 import
import { Hero } from "./Hero.jsx";

23.4 Props 이름 불일치

<Profile userName="홍길동" />

function Profile({ name }) {
  return <h2>{name}</h2>; // undefined
}

부모와 자식의 이름을 동일하게 합니다.

<Profile name="홍길동" />

23.5 구조 분해 중괄호 누락

function Profile(name) {
  return <h2>{name}</h2>;
}
function Profile({ name }) {
  return <h2>{name}</h2>;
}

23.6 문자열과 숫자 혼동

<Avatar size="120" /> // 문자열
<Avatar size={120} /> // 숫자

계산이나 width 값에 사용할 숫자는 중괄호로 전달합니다.

23.7 Props 직접 변경

부모가 전달한 객체, 배열과 값을 자식에서 직접 변경하지 않습니다. 화면 변경은 새로운 Props 또는 State로 수행합니다.

23.8 children을 렌더링하지 않음

function Card({ children }) {
  return <div className="card"></div>;
}

부모가 전달한 내용이 표시되려면 {children}을 원하는 위치에 작성합니다.

function Card({ children }) {
  return <div className="card">{children}</div>;
}

23.9 spread로 의도하지 않은 Props 전달

DOM 요소에 사용자 컴포넌트 전용 prop을 그대로 펼치면 브라우저 경고나 의도하지 않은 속성이 생길 수 있습니다. 필요한 DOM props만 선별합니다.

24 컴포넌트와 Props 점검

  1. 컴포넌트 이름이 대문자로 시작하는가?
  2. 하나의 명확한 UI 역할을 담당하는가?
  3. 다른 컴포넌트 함수 안에 정의하지 않았는가?
  4. export와 import 방식이 일치하는가?
  5. 부모와 자식의 prop 이름이 일치하는가?
  6. 문자열 이외의 값에 중괄호를 사용했는가?
  7. Props를 구조 분해할 때 {}를 사용했는가?
  8. Props를 직접 변경하지 않는가?
  9. 기본값이 undefined에만 적용됨을 고려했는가?
  10. children을 전달했다면 자식 컴포넌트가 렌더링하는가?
  11. spread 사용이 실제로 필요한가?
  12. 컴포넌트 이름과 Props 이름만으로 역할을 이해할 수 있는가?
  13. 시맨틱 HTML과 접근성을 컴포넌트 내부에서도 유지하는가?
  14. App을 읽었을 때 웹사이트의 큰 구조가 보이는가?
